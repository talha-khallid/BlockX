BlockX Help

Setting up shared settings, and locking the browser down so this cannot be walked around.

What syncs where

BlockX keeps one set of settings across everything you use, through two layers that work independently. Whichever ones are available are kept in step automatically.

No setup

Account sync

Every profile signed into the same Google account, on any device. Already running.

One command

Settings file

Every profile on this machine, whatever account each one uses — which account sync alone cannot do.

Why the file needs a helper

A Chrome extension cannot read or write ordinary files. That is a hard boundary in the browser, not an oversight, so reaching a real file on disk needs a small program living outside the sandbox that the browser is told about explicitly. That is native/blockx_host.py: about a hundred lines that do nothing but read and write one JSON file. It never looks at what your settings mean.

Skip this and nothing breaks — you just get account sync on its own.

Install it

Needs Python 3, which macOS and Linux already have. On Windows, install it from python.org and tick Add Python to PATH.

cd <the BlockX folder>/native
python3 install.py

Then quit the browser completely and reopen it — registrations are only read at launch. Open the dashboard and look under General → Shared Settings: the settings file row turns green and shows its path.

You run this once per machine, not once per profile. Chrome keeps the registration at the root of its user data directory, so every profile inside it picks up the same one.

Where the file lives

Linux~/.config/blockx/settings.json
macOS~/Library/Application Support/BlockX/settings.json
Windows%APPDATA%\BlockX\settings.json

It appears the first time a setting changes. If it already exists when a new profile starts, that profile adopts it.

Under Flatpak the browser's own config path points inside its sandbox, so the helper deliberately ignores it and uses your real home. One file, shared by everything.

Editing the file by hand

You are welcome to read it. Editing is another matter: everything BlockX writes is checksummed, so a file that no longer matches its checksum is treated as untrusted. Edits that tighten protection are accepted. Edits that loosen it are ignored and the file is rewritten.

That exists so the file cannot be used to skip the twelve-minute wait that removals go through. It is a deterrent, not a lock — the recipe is in the source, and anyone who reads it can get round it. Same as everything here: it works because you want it to.

When it does not work

The settings file row stays orange.
Quit the browser completely and start it again. On Linux, check the installer actually listed the browser you use.
"Specified native messaging host not found" in the console.
The browser you are using was not among those the installer found. Run it again and read the list it prints.
Nothing appears in the file.
It is written on the first change. Toggle something in the dashboard and look again.
Remove the helper.
python3 install.py --uninstall. Your settings file is left alone.

Make the browser enforce it

An extension can be switched off from a menu. A browser policy cannot — it is read from a location only an administrator can write, and the browser applies it before any profile loads. Guest windows, new profiles and Incognito all bypass an extension entirely; this is the only thing that closes those.

    Flatpak browsers: quit properly
    
                
    A Flatpak browser cannot see the host's /etc directly. Its launcher
                   copies the policy files in as symlinks once, when the browser starts,
                   and never again. A file written after that point is invisible to the running browser,
                   however many windows you close and reopen, because the sandbox from the original
                   launch is still alive.
    
                
    So on Flatpak, quit the browser properly first — its own Quit,
                   or closing every window and letting it exit — and start it again. That is usually
                   enough, and it is the only way that keeps your settings.
    
                
    Only if it still has not taken effect, force it:
    
                
    
                    
    flatpak kill com.google.Chrome
    
                    
                
    
                
    Substitute the app id for your browser — com.brave.Browser,
                   org.chromium.Chromium. If you are not using Flatpak, ignore this card.
    
            
    

            
    
                
    Killing the browser costs you settings
    
                
    flatpak kill, pkill and Force Quit all stop the browser
                   dead. Chrome writes its preferences periodically and on a clean exit, so anything
                   changed since the last write is simply lost.
    
                
    Developer Mode is one of those preferences. Lose it and every
                   extension you loaded from a folder is switched off the next time the browser
                   starts — which looks exactly like the extension having uninstalled itself.
    
                
    If that happens: open chrome://extensions, turn
                   Developer Mode back on, load the folder again, and then quit the browser properly
                   so the setting is written to disk.
